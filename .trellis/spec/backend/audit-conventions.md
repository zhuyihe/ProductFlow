# Audit Conventions

Project rule. Every backend change that touches user data or administrative
actions must comply.

## Why

Administrators can access user-owned business data for support and risk review.
Every such access must be auditable. Session revocation and destructive
moderation actions must remain attributable so support actions do not become
silent data loss.

## What Must Be Audited

1. **Admin user-content access.** Any time a principal whose `kind == "admin"`
   explicitly opens user content outside the normal self-scoped workspace.
2. **Admin gallery moderation.** Public gallery reads are not audited, but
   admin destructive/moderation actions on another user's gallery content are.
3. **Admin session revocation.** Revoke/demote operations that immediately
   remove access are audited like other cross-user destructive actions.
4. **Future: tenant-scoping mutations.** When admins re-attribute resources
   (move products to a different owner), that mutation is auditable per (1).
5. **Atelier model-call events.** Every Atelier-originated New API relay call
   should write a `model_call` event so users can see their own usage records
   and admins can audit failures, models, groups, and request ids.

What is **not** audited:

- Normal user actions on their own data. Use business event logs for those.
- Admin using the normal workspace as themselves. Normal `/products`,
  `/image-sessions`, and product workbench APIs are self-scoped even for admin
  principals and are not cross-user audit events.
- Admin `GET /api/gallery` and `GET /api/gallery/{id}` reads. Gallery rows are
  public to authenticated users once shared.
- Admin deleting their own gallery entry. Treat it like a normal owner action.
- Health checks and unauthenticated requests.
- Password-admin login is gone; there is no HTTP login attempt to audit.

## Unified Event Ledger

`audit_events` is the forward-looking fact table for both user-visible usage
records and admin audit center views. New code that records Atelier business
or support activity should prefer this event stream.

Core event types:

- `model_call`: one row per text/image relay call originated by Atelier.
- `admin_content_view`: admin explicitly opened user-owned content from the
  audit center.
- `settings_change`, `session`, `export`: reserved for operational events.

Rules:

- Ordinary users may query only events whose `subject_user_id` equals their
  current New API user id.
- Admin audit APIs may query cross-user metadata, but generated content is
  hidden until an explicit content-view endpoint writes `admin_content_view`.
- Event payloads must not include raw tokens, API keys, full prompts, raw
  provider request/response bodies, or base64 image data.
- New API quota is the billing fact source. Atelier records New API facts
  such as quota, model, group, token name, and request id; it must not
  recalculate final prices locally for display.

## Scenario: Atelier model-call ledger reconciliation

### 1. Scope / Trigger

- Trigger: changing Atelier text/image provider calls, workflow/image-session generation, New API relay headers, New API
  log APIs, or `audit_events` helper behavior.
- Applies to every Atelier-originated model call that sends `X-Atelier-Request-Id` through New API.

### 2. Signatures

- Atelier header: `X-Atelier-Request-Id: str`, generated by `generate_atelier_request_id()`.
- Atelier DB row: `AuditEvent(event_type="model_call", atelier_request_id=<id>)`.
- New API token log lookup: `GET /api/log/token?atelier_request_id=<id>` with `Authorization: Bearer <new_api_token>`.
- New API log facts copied into Atelier:
  `id`, `request_id`, `upstream_request_id`, `token_id`, `token_name`, `group`, `model_name`, `quota`,
  `prompt_tokens`, `completion_tokens`, `use_time`, and `type`.

### 3. Contracts

- One real provider call equals one `model_call` event and one `atelier_request_id`. A provider that truly supports batch
  generation may use one event for the one batch relay request and must record `batch_count`; wrapper code must not fake
  batch support by looping multiple provider calls under one request id.
- `audit_events` helpers must not commit the caller's business transaction. They may `flush` so the event id is available.
- SQLAlchemy `Session` instances are thread-bound. Provider worker threads must not create/update audit events using the
  caller session; they return results/errors to the orchestration thread, which updates events.
- After the relay returns or raises, Atelier queries New API by `atelier_request_id` with the same token that made the
  call. New API scopes this lookup to the authenticated token id and must not return other users' logs.
- If New API returns a matching log, Atelier copies log facts into the audit row and treats quota/tokens/use time as
  settled. If no log is found for a successful provider result, `quota` stays `null` and metadata records
  `billing_lookup_status = "not_found"` instead of pretending the call was free.
- If no log is found for a failed provider result, Atelier may set `quota = 0` only with
  `billing_lookup_status = "not_found"` metadata. Lookup transport failures leave `quota = null`.
- Audit metadata and error text must not contain raw tokens, API keys, prompts, request bodies, base64/data URLs, full
  provider response bodies, or tracebacks.

### 4. Validation & Error Matrix

- New API consume/error log found -> audit row gets `new_api_log_id`, request ids, model, group, quota, tokens, and
  `billing_lookup_status = "found"`.
- Successful provider result and no New API log -> `status = "succeeded"`, `quota = null`,
  `billing_lookup_status = "not_found"`.
- Failed provider result and no New API log -> `status = "failed"`, `quota = 0`,
  `billing_lookup_status = "not_found"`.
- New API lookup network/API failure -> preserve local status, `quota = null`, `billing_lookup_status = "lookup_failed"`.
- Missing New API token/context -> skip remote lookup and record `billing_lookup_status = "skipped"`.
- Provider thread tries to update audit with caller session -> blocking bug; refactor to main-thread event settlement.
- Error contains `sk-`, bearer token, URL query secrets, `prompt=`, `data:image/...;base64`, request body, or traceback ->
  persist a generic safe failure message.

### 5. Good/Base/Bad Cases

- Good: an image-session task requests two Images API candidates in one `n=2` request, writes one event with
  `batch_count = 2`, then copies the one New API consume log quota into that event.
- Good: a workflow image node with two downstream references and a non-batch provider creates two providers, two request
  ids, and two audit events, even if the provider calls run concurrently.
- Base: local mock/provider execution without a New API token writes local status and `billing_lookup_status = "skipped"`.
- Bad: writing `quota=Decimal("0")` for every success before checking New API.
- Bad: using `/api/log/` admin lookup from Atelier to reconcile ordinary user model calls.
- Bad: calling `session.commit()` inside `create_audit_event()` while a workflow node has only flushed intermediate
  artifacts.

### 6. Tests Required

- ProductFlow audit helper test: `create_audit_event()` and `update_audit_event()` flush but do not commit caller
  transactions.
- ProductFlow reconciliation test: successful model-call updates copy New API facts and no-log success keeps quota unknown.
- ProductFlow failure test: failed model-call sanitizes errors and distinguishes no-log zero from lookup failure unknown.
- ProductFlow workflow image test: non-batch multi-target generation creates distinct request ids/events and does not
  write DB from provider threads.
- ProductFlow admin content-view test: mismatched `event_id` resource payload returns `400` and writes no event.
- New API model/controller test: token log lookup by `atelier_request_id` returns only logs for that token id and preserves
  the actual log id needed by Atelier.

### 7. Wrong vs Correct

#### Wrong

```python
event = create_audit_event(session, status="running")
result = provider.generate(...)
update_audit_event(session, event_id=event.id, status="succeeded", quota=Decimal("0"))
```

This commits the caller transaction inside the helper and records a fake settled cost.

#### Correct

```python
event = create_audit_event(session, status="running", atelier_request_id=request_id)
try:
    result = provider.generate(...)
finally:
    facts = lookup_new_api_log_facts(token=context.new_api_token, atelier_request_id=request_id)
    settle_model_call_event(session, event_id=event.id, facts=facts)
```

The provider result is recorded, the New API log is copied when available, and billing remains unknown instead of fake
zero when lookup cannot prove the final cost.

## Legacy Audit Helpers

`application/audit_logs.py` exposes:

```python
def record_admin_user_content_access(
    session, *, principal, target_user_id, action,
    resource_type, resource_id, request_context,
) -> None:
    ...
```

That helper:

- Commits independently of the surrounding business transaction so a business
  rollback does not erase the audit trail.
- Truncates over-long fields to fit column widths.
- Uses the authenticated principal's `new_api_user_id` when present and
  falls back to `emergency-admin` only for CLI/bootstrap-style admin actors
  that do not have a user id.

`audit_logs` remains for compatibility with existing routes and tests. Do not
expand it for new usage-record or audit-center features; add the corresponding
`audit_events` writer instead.

## Action Naming

Stable, lowercase, underscore-separated. The contract: `<verb>_<noun>` or
`admin_<event>`. Examples:

- `read_product`, `update_product`, `delete_product`
- `read_image_session`, `retry_image_generation_task`
- `delete_gallery_entry`, `resolve_gallery_report`, `revoke_auth_session`
- `model_call`, `admin_content_view`

Do not embed dynamic data in the action string (no `delete_product_42`); put
the id in `resource_id`.

## Outcome Field

`audit_logs.outcome` was added so admin access can be recorded at multiple
moments:

- `intent` (default): "admin reached the route". Acceptable for read paths.
- `success`: business action completed and committed.
- `denied`: authorization rejected the action after the audit context was
  established (rare; usually 403 is raised earlier).
- `error`: business action raised after intent was recorded.
- `legacy_access` (reserved): admin touched a record whose owner predates the
  tenant rollout. Not used at `image.aync.cc.cd` because the deploy was fresh.

For read-only paths, recording `intent` at the entry point is enough. For
mutating paths, prefer recording the final `outcome` so audit reflects
actual behavior. The Wave 2 `audit_action` context manager wraps this:

```python
with audit_action(session, principal, action="update_product",
                  resource_type="product", resource_id=pid,
                  request_context=ctx) as audit:
    do_business_logic()
    audit.mark_success(details={"changed_fields": [...]})
```

## Where Calls Live

- Routes layer (`presentation/routes/*.py`) initiates admin audit calls.
- Application/provider orchestration may initiate `model_call` events because
  the route layer does not own every background worker relay call.
- Application layer does not call audit directly; it raises or returns; the
  route decides whether the admin outcome warrants `success`/`error`.
- Background workers do not write admin content audit; their model calls still
  write `model_call` usage events for the user who enqueued the task.

## Reviewing New Code

When reviewing a route change:

1. Is the route admin-accessible? If yes, does it call
   `record_admin_user_content_access`, `audit_action`, or an `audit_events`
   helper for the path that explicitly touches cross-user data?
2. Is the action name stable and verb_noun shaped?
3. Is `target_user_id` correctly populated from the resource's owner, not the
   admin's id?
4. Are `client_address` and `user_agent` passed via `AuditRequestContext`?

Gallery-specific review rule:

- Do not audit admin `GET` reads of public gallery content.
- Do audit admin deleting another user's gallery entry, resolving/dismissing a
  report, or revoking a session for immediate demotion.
- Do not audit an admin deleting a gallery entry they authored themselves.

Usage/audit-center review rule:

- Do not add cross-user data access to ordinary workspace routes.
- Do not return user-generated content from audit list/detail endpoints by
  default.
- Do record `admin_content_view` before returning user content from an admin
  explicit content endpoint.
- Do record failed model calls with safe error details and the correlated
  `atelier_request_id` / New API request id when available.

## Anti-Patterns (Do Not Reintroduce)

```python
# WRONG: admin action with no audit
@router.delete("/admin/products/{pid}")
def admin_delete_product(pid, principal=Depends(require_admin_audit_principal)):
    delete_product(pid)
    return Ok()

# WRONG: audit recorded after business commit, so a crash between them loses the
# audit trail entirely
def admin_route(...):
    result = do_business()
    session.commit()
    record_admin_user_content_access(...)   # may never run

# WRONG: action string embedding dynamic data
action="delete_product_" + pid

# WRONG: admin action audit attributing to the wrong user
record_admin_user_content_access(..., target_user_id=principal.new_api_user_id, ...)
# target_user_id is the resource owner, not the admin
```

## Retention

Audit rows are not truncated by the application; deletion is an operations
decision. Plan to add a retention job once table size exceeds operational
comfort (currently no concern at fresh deploy).
